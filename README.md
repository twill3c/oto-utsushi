# 音写ラボ(oto-utsushi)

青空文庫の一節を**声に出して読み**、ブラウザの中で完結する音声認識の出力を原文と
突き合わせて、**機械が聞き落とす場所**を原文の上に描く。

音声認識のアプリはたいてい「認識結果」を出して終わる。その結果が正しいかは誰も知らない。
ここでは順序を逆にした — **正解が先に画面に在り**、それを読み上げる。
だから認識の誤りを厳密に測れる。測るのは人の滑舌ではなく、機械の側の癖である。

## 実行時課金ゼロの構成

| | |
|---|---|
| 推論 | 100% クライアント。サーバ関数を持たない(`output: "export"`) |
| モデル重み | Hugging Face の CDN から取る。**リポジトリにも Vercel にも置かない** |
| 音声素材 | 0 バイト(ユーザのマイクのみ)。録音は保存も送信もしない |

Vercel の無料枠が崩れる経路は「重みを `public/` に置く」ことだけなので、
そこを非機能要求(N-03)にして検査で固定している。

## 測っているもの

- **厳密 CER** — 正規化後の字面で測る文字誤り率
- **表記ゆれ許容 CER** — 読みを変えない変換(カタカナ→ひらがな・繰り返し記号の展開・
  位取りを含む漢数字)で説明できる差を一致に数え直したもの。**分母は厳密側と揃えてある**
- 置換 / 脱落 / 余分の内訳、読み飛ばし(連続削除)、言い直し、読速

二つの CER に上下関係は無い。繰り返し記号の展開は直前の一字の誤りを二字に広げるため、
許容側が厳密側を上回ることがある(SPEC §4 に実測を書いた)。

## 循環の禁止

**参照テキストを認識器へ渡さない。** Whisper の `initial_prompt` に課題文を入れれば
CER は劇的に下がるが、それは自分の答案を採点に混ぜているだけである。
型・実行時アサート・静的検査の三重で塞いでいる。

## モデルと実行系

| | 初回に落ちる量(実測 2026-08-29) |
|---|---|
| whisper-base(既定) | WebGPU 206 MB ／ WebAssembly 122 MB |
| whisper-tiny | WebGPU 114 MB ／ WebAssembly 66 MB |

日本語特化の `kotoba-whisper-v2.2-ONNX` は実在し transformers.js にも対応しているが、
large-v3 蒸留でエンコーダが大きく、最小の組み合わせでも **534 MB** ある。
初回に落とさせる量ではないので採らなかった（記録は `src/core/models.ts`）。

実行系(ONNX Runtime の wasm)は**版を固定した CDN から取り、成果物には載せない**。
webpack が黙って 23.6 MB を複製していたのを loop_002 で見つけて外した
（成果物 25.0 MB → 1.41 MB）。`npm run verify` の `bundle` 段が現物を検査する。

WebAssembly 側のデコーダが 8 bit にできないのは、ONNX Runtime 1.26.0-dev の QDQ 最適化が
`decoder_model_merged` の q8 / int8 / uint8 を読み込めないため（loop_003 実ブラウザ実測）。
通るもののうち最小の fp16 を採っている。**この故障は単体テストにもビルドにも出なかった。**

## 実ブラウザ検品

```bash
npm run speech    # 課題文を日本語 TTS で読ませて WAV を作る
npm run browser   # Chromium で out/ を開き、疑似マイクから全経路を通す
```

マイク → 録音 → 16 kHz リサンプル → Whisper → アライメント → 計量 を一続きに走らせる。
実測 2026-08-29（whisper-base / WebAssembly / 19.3 秒の合成音声）: 厳密 CER 45.5%。

**この数字は品質ではない。** TTS は人の音読の代わりにならないし、SAPI の読み誤りが
ASR の誤りに混ざる。見ているのは「経路が通ること」だけである。
